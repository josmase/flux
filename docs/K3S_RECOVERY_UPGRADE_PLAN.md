# K3s upgrade plan for recovery

Status: first K3s stage partially completed; worker upgrades paused after a drain disrupted storage and workloads. No CloudNativePG upgrade has been performed. This plan is part of [the recovery strategy](RECOVERY_STRATEGY_PLAN.md).

## Objective and version path

Move from K3s `v1.31.14+k3s1` to a currently supported Kubernetes release supported by a currently supported CNPG and Barman Cloud plugin combination. Candidate final minor: Kubernetes 1.35; verify the currently supported versions and exact K3s, CNPG, plugin and image digests immediately before the maintenance window. CNPG 1.30's published matrix includes Kubernetes 1.35, but its support dates and the newest supported release must be rechecked at execution time.

Do not skip Kubernetes minor versions: upgrade the full cluster through **1.32 → 1.33 → 1.34 → 1.35**, one minor at a time. The existing inventory currently proposes `v1.32.13+k3s1` for the first stage; verify its upstream checksums and release notes. Select and record exact versions for the remaining stages before implementation. Recheck component compatibility and Kubernetes API removals at each stage. Control-plane servers must be upgraded one at a time before agents; preserve Kubernetes version-skew rules.

The current CNPG 1.25.1 is out of support. Its published Kubernetes support range ends at 1.32, so simply carrying it through all four stages is not an approved compatibility assumption. The user has waived the disposable-environment rehearsal; review upstream compatibility for every transition, including an intermediate CNPG version if needed, and document any temporarily unsupported combination and the shortest exposure window before proceeding. Resolve this compatibility bridge before upgrading beyond 1.32. The target is a supported combination, not permanent use of CNPG 1.27.

4. **Complete K3s 1.32 workers serially.** Refresh the baseline and confirm capacity before each worker, beginning with 204 only after the above issues are resolved. Before the next node, confirm its reported version and Ready status, both databases 3/3 and replicating, critical applications and LINSTOR healthy, and all evicted critical pods recovered. Apply the same checks to 205, 206 and the GPU worker in an order based on live placement. If the chosen reduced-redundancy window intentionally permits a member to stay pending during a single drain, require it to recover before the next drain.
5. **Bridge CNPG and finish the version path.** Once every node is at 1.32, verify the current CNPG support matrix and release notes, then choose and pin exact sequential operator releases that overlap the current and next Kubernetes versions. The installed CNPG 1.25.1 and intermediate releases may be out of support; minimize and record that exposure. Check CRD and instance-manager upgrade behavior and validate both clusters at every operator step. Do not advance to Kubernetes 1.33 until the bridge is explicitly established. Then proceed one Kubernetes minor at a time, servers serially before workers, with a fresh recovery bundle and full stage checks at each step. Select a currently supported final K3s/CNPG/Barman combination immediately before execution rather than assuming 1.35 remains the right target.
6. **Close the stage and resume recovery implementation.** Record versions, health checks, placement decisions, failures, backup evidence and deviations in this document and the recovery plan, and commit and push them. Rotate the legacy S3 credential exposed in diagnostic output through the encrypted GitOps workflow, after checking historical snapshot retry and recovery effects. Proceed with the new backup system and its restore drills; do not claim the one-hour recovery point or eight-hour restore target until measured.

**Stop conditions:** unexpected loss of quorum, failed drain or scheduling, controller/CSI unavailability, replication or database degradation beyond the explicitly planned single-node window, storage degradation, lost critical application availability, or a node failing to return Ready. Uncordon when safe, restore service and collect sanitized diagnostics. Do not use a binary downgrade as an assumed datastore rollback.

Stop on any unmet check.
4. After all nodes reach a stage, verify exact node versions, control-plane health, networking, DNS, storage, Flux, backup freeze, application and database health. Check the kube-vip reconciliation behavior against the current inventory before allowing the playbook's final kube-vip step. Record evidence, update inventory targets for the next minor, and repeat with a new verified snapshot.
5. On a supported Kubernetes target, upgrade CNPG and install the compatible pinned plugin through Flux after reviewing that exact path; the user waived a disposable rehearsal, so record the resulting untested transition risk. Validate all replicas, recovery configuration and restore drills before enabling production backup schedules.

## Failure and recovery

Stop immediately on lost quorum, degraded storage, unexpected pod termination, data inconsistency, blocked drain or failed node readiness. Preserve diagnostics and existing backups. Do not assume a K3s binary downgrade safely rolls back an upgraded datastore: use the tested K3s snapshot restore procedure with the matching token and compatible software, and perform application recovery from independently verified backups if needed. Record the outcome in the living plan before another attempt.
