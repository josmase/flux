# K3s upgrade plan for recovery

Status (2026-11-11): all seven active nodes run K3s 1.35.9 and CloudNativePG 1.30.1; both PostgreSQL clusters are healthy 3/3. Maintenance remains active. The user requested continuing to the latest K3s version and restoring workloads after completion. Target 1.37.2 via 1.36.6, one minor at a time. CNPG 1.30 lists Kubernetes 1.37 as tested but unsupported; this is a documented compatibility exception to the original supported-combination objective. No 1.36 node upgrade has started. Fresh pre-upgrade recovery points and storage/backup health must be re-established first. This plan is part of [the recovery strategy](RECOVERY_STRATEGY_PLAN.md).

## Objective and version path

Move from K3s `v1.31.14+k3s1` to a currently supported Kubernetes release supported by a currently supported CNPG and Barman Cloud plugin combination. Candidate final minor: Kubernetes 1.35; verify the currently supported versions and exact K3s, CNPG, plugin and image digests immediately before the maintenance window. CNPG 1.30's published matrix includes Kubernetes 1.35, but its support dates and the newest supported release must be rechecked at execution time.

Do not skip Kubernetes minor versions: the completed path is **1.32 → 1.33 → 1.34 → 1.35**; continue **1.36 → 1.37** one minor at a time. Current targets are `v1.36.6+k3s1` and `v1.37.2+k3s1`, the latest published releases verified from K3s release notes on 2026-11-11. Recheck exact versions, release notes and checksums immediately before each stage. Control-plane servers must be upgraded one at a time before agents; preserve Kubernetes version-skew rules. The user's latest-version request accepts the CNPG 1.30 / Kubernetes 1.37 tested-but-unsupported combination pending a future CNPG release that supports 1.37.

The current CNPG 1.25.1 is out of support. Its published Kubernetes support range ends at 1.32, so simply carrying it through all four stages is not an approved compatibility assumption. The user has waived the disposable-environment rehearsal; review upstream compatibility for every transition, including an intermediate CNPG version if needed, and document any temporarily unsupported combination and the shortest exposure window before proceeding. Resolve this compatibility bridge before upgrading beyond 1.32. The target is a supported combination, not permanent use of CNPG 1.27.

## Direct CNPG 1.30.1 upgrade: feasibility and execution plan

**Original assessment, 2026-11-10:** Consider one Flux-managed operator upgrade from CNPG 1.25.1 (chart 0.23.2) directly to CNPG 1.30.1 (chart 0.29.1), followed promptly by K3s 1.33 and 1.34 one minor at a time. This direct candidate supersedes the multi-step CNPG bridge below for planning; at the time it was not yet ready for execution. No operator, CRD or database changes were made during that assessment; the subsequently authorized upgrade was completed as recorded below. CNPG recommends upgrading releases sequentially, so skipping 1.26–1.29 is a deliberate deviation. Review every intervening release note and upgrade instruction, and establish that none forbids the exact jump before deciding to proceed.

**Feasibility so far: promising, not proven.** The [CNPG support matrix](https://cloudnative-pg.io/docs/1.30/supported_releases/) lists Kubernetes 1.32 and 1.33 as tested but unsupported by CNPG 1.30; Kubernetes 1.34–1.36 are in its supported range. Upgrading CNPG while still on K3s 1.32 therefore creates an explicitly unsupported combination, lasting until the cluster reaches a supported target; K3s distribution support is a separate question. The previously requested supported end state does not imply that this transitional combination has been validated. The user permits downtime and has waived a disposable rehearsal, but data-loss and support risks remain. Record the transitional support exception as part of the execution decision, and schedule the 1.33 and 1.34 stages close together rather than treating 1.32/1.30 as the destination.

## Failure and recovery

Stop immediately on lost quorum, degraded storage, unexpected pod termination, data inconsistency, blocked drain or failed node readiness. Preserve diagnostics and existing backups. Do not assume a K3s binary downgrade safely rolls back an upgraded datastore: use the tested K3s snapshot restore procedure with the matching token and compatible software, and perform application recovery from independently verified backups if needed. Record the outcome in the living plan before another attempt.
