# Stop 3: GitLab 18.5.7 / chart 9.5.7

**Theme:** Required 18.x patch stop after the dedicated-service recovery.
**Risk:** Medium operational risk; no intended database, Valkey, storage, or
ingress topology change.
**Window:** Suspended manual window; one stop only.

This stop uses the mandatory [operating standard](11-operational-standard.md).
It supersedes the former shared-CNPG and bundled-Redis instructions.

## Stop-specific preflight

- [ ] Stop 2 acceptance is recorded: GitLab HelmRelease is `9.2.8` Ready,
  `gitlab-postgres` has three Ready instances, `gitlab-valkey` is Ready, and
  Gitaly passes `gitlab:gitaly:check`.
- [ ] No pending or failed Rails/background migrations from 18.2.8.
- [ ] `gitlabhq_production` and `registry` fresh dumps have actual, recorded
  SHA-256 values and off-cluster copies.
- [ ] Current CNPG extensions and capacity are recorded. `amcheck` is not a
  required change for this stop; do not add extensions merely to match an old
  runbook.
- [ ] Rendered chart `9.5.7` diff contains only the intended version/image
  changes and retains external PostgreSQL, Valkey, disabled chart ingress, and
  the existing Traefik routes.

## Required manifest change

Update the GitLab chart target from `9.2.8` to `9.5.7`. Do not change the
database host, generated DB Secrets, Valkey endpoint, repository PVC, or
ingress model in the same stop.

## Window procedure

Follow Sections 2–5 of the operating standard. The version-specific order is:

1. Suspend `apps-gitlab` and the GitLab HelmRelease; record the deployed Helm
   revision and Flux source revision.
2. Stop writers only after the verified dumps are complete.
3. Apply the rendered `9.5.7` values manually with a recorded timeout. Treat
   a migration Job failure or a Gitaly attach failure as a stop condition.
4. Wait for the migrations, then restore writers.
5. Verify web health, Gitaly, Registry read/write, Git SSH/HTTP access, a
   runner job, and `gitlab:background_migrations:status`.
6. Push the accepted version commit and resume Flux only after all checks
   pass; verify the complete Flux chain is Ready at that revision.

## Acceptance criteria

| Check | Expected evidence |
| --- | --- |
| Chart and release | GitLab HelmRelease Ready at `9.5.7`; Helm history shows a deployed revision. |
| Application | GitLab version is `18.5.7-ee`; `/-/health` succeeds. |
| Database | CNPG has three Ready instances; generated GitLab and Registry credentials connect; no pending standard migrations. |
| Storage | Gitaly is Ready; its LINSTOR volume exposes `/dev/drbd…`; `gitlab:gitaly:check` passes. |
| Valkey | Authenticated `PING` succeeds and application/Sidekiq workloads are Ready. |
| User paths | Disposable Git clone/push, Registry push/pull, and one runner job succeed. |
| GitOps | Source, infrastructure, GitLab bootstrap/database bootstrap, GitLab, and runner Kustomizations/HelmReleases are Ready. |

## Rollback boundary

Before accepting any irreversible migration, return to the recorded `9.2.8`
Helm revision and Git commit while writers remain stopped. If database state
must be restored, use the verified stop dump and the strict restore procedure;
do not attempt to repair object ownership manually.

## Change record additions

Record dump SHA-256 values, chart render diff review, migration Job name and
result, Gitaly device path/replica state, Flux revisions, Registry evidence,
and any exception to the operating standard.
