# Stop 5: GitLab 18.11.14 / chart 9.11.16

**Theme:** Final 18.x compatibility and readiness stop before the chart-10
transition.
**Risk:** Medium; this stop is deliberately narrow so that chart-10 changes
are isolated in Stop 6.
**Window:** Suspended manual window.

Use the mandatory [operating standard](11-operational-standard.md).

## Stop-specific preflight

- [ ] Stop 4 is accepted; all prior background migrations are complete.
- [ ] Dedicated CNPG is PostgreSQL 17 and has backup/capacity evidence. Do not
  upgrade PostgreSQL in this application stop.
- [ ] Dedicated Valkey, Gitaly, Registry, Traefik routes, and Flux dependency
  chain are all Ready.
- [ ] The `9.11.16` render is reviewed against `9.8.12`; it retains external
  PostgreSQL/Valkey, disabled chart ingress, and all Gitaly persistence.
- [ ] The chart-10 render is prepared and reviewed separately, but it is not
  committed to or applied by the Stop 5 release branch. This prevents a
  “validation” stop from smuggling in a major chart transition.
- [ ] Review Stop 4's recovery record. During the migration phase,
  `wait-for-deps` restarts and temporarily unready Webservice pods are expected
  until the migration Job completes; do not let an automated rollback run
  against a database that has already advanced. Suspend the HelmRelease,
  capture post-attempt dumps, and recover forward if a migration-bearing
  attempt is interrupted.

## Required manifest change

Update chart `9.8.12` to `9.11.16` only. Keep the current dedicated-service
configuration unchanged.

`10.2.10` renders. The review must enumerate every removed/added Service,
StatefulSet, PVC reference, CRD, ingress, Secret reference, and Registry
storage configuration. No destructive resource deletion is authorized by this
preparation step.

### Recovery and learnings

- Chart `0.89.0` deployed Runner `19.0.0`, not an 18.11-line Runner. Verify
  the chart's rendered application image, not only a chart-index adjacency;
  `0.88.4` is the correct Runner `18.11.4` artifact.
- A direct Helm upgrade against a suspended Flux-owned release can fail on
  server-side-apply ownership conflicts even after upgrade hooks or migrations
  start. For a Flux-owned GitLab release, use the HelmRelease/controller for
  recover-forward work.
- Do not let the GitOps source retain the previous chart version after a
  migration-bearing forward release succeeds. It can initiate an unsafe
  downgrade. Push the accepted target commit as soon as GitLab Git access is
  available; keep `apps-gitlab` suspended until that source is authoritative.
- If Helm is left with a stale `pending-upgrade` Secret label, first inspect
  the encoded release status. In this incident the release payload was already
  `superseded`; correcting only the Secret's `status` label cleared the lock.
- New Gitaly images can take several minutes to pull and the PVC can briefly
  report a multi-attach conflict while the old Pod terminates. Treat both as
  stop-and-observe conditions; do not delete the retained repository PVC.
