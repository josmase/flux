# Stop 4: GitLab 18.8.11 / chart 9.8.12

**Theme:** Required 18.x patch stop and dedicated-Valkey regression gate.
**Risk:** Medium; Valkey already became external in Stop 2. This stop must not
attempt a second Valkey migration.
**Window:** Suspended manual window.

Use the mandatory [operating standard](11-operational-standard.md).

## Stop-specific preflight

- [ ] Stop 3 is accepted and all background migrations are complete.
- [ ] `gitlab-valkey` is the only GitLab cache endpoint configured in rendered
  values. It requires authentication, has AOF enabled, and its persistence
  probe has been recorded.
- [ ] The generated `gitlab-external-db` and `gitlab-registry-external-db`
  Secrets exist and application connections succeed. Do not replace them with
  SOPS-managed application passwords.
- [ ] Fresh Rails and Registry dumps are verified by actual SHA-256 and stored
  off-cluster.
- [ ] Rendered chart `9.8.12` output retains the dedicated CNPG/Valkey
  endpoints, disabled chart ingress, and the existing Gitaly PVC claim.

## Required manifest change

Update chart `9.5.7` to `9.8.12` only. The existing dedicated `gitlab-valkey`
StatefulSet and auth Secret are production dependencies, not temporary setup
objects. Do not create an alternative standalone Valkey, change namespaces, or
delete a legacy PVC during this stop.

## Window procedure

Follow the operating standard. Restore webservice first after the Helm
upgrade, then prove it can reach authenticated Valkey and the generated
database endpoint. Restore Sidekiq next, then Registry, KAS, Shell, and the
remaining workers. This ordering narrows the blast radius if cache or database
configuration regresses.

## Acceptance criteria

| Check | Expected evidence |
| --- | --- |
| Chart and application | GitLab HelmRelease Ready at `9.8.12`; GitLab reports `18.8.11-ee`; web health succeeds. |
| Valkey | Unauthenticated `PING` is rejected; authenticated `PING` is `PONG`; a persisted probe survives a controlled Valkey Pod restart only if such a restart is approved for the window. |
| Application cache use | Webservice and Sidekiq are Ready without Redis/Valkey connection errors. |
| Database and storage | CNPG, generated credential connections, Gitaly device path, and `gitlab:gitaly:check` pass. |
| User paths | Git clone/push, Registry push/pull, and a runner job pass. |
| GitOps | The full source-to-GitLab Flux dependency chain is Ready at the accepted commit. |

## Rollback boundary

Rollback to the recorded Stop 3 chart and Git commit before accepting a failed
migration. Preserve the dedicated Valkey PVC and auth Secret: they are not a
rollback disposable. Restore a database only from the verified stop dump when
the database state—not merely the application chart—is the failure.

## Change record additions

Include the rendered Redis/Valkey configuration, auth and persistence probe
results, application cache logs, dump SHA-256 values, and the Flux handoff
revision.
