# Stop 7: GitLab 19.5.3 / chart 10.5.4

**Theme:** Final application target and Duo checkpoint migration monitoring.
**Risk:** Medium-to-high; the chart change is narrow, but the background
migration can consume material database capacity after the maintenance window.
**Window:** Suspended manual window, followed by an explicit monitoring period.

Use the mandatory [operating standard](11-operational-standard.md).

## Stop-specific preflight

- [ ] Stop 6 is accepted, including Registry `s3_v2` push/pull/delete evidence.
- [ ] CNPG has capacity evidence for the expected Duo checkpoint growth; record
  free space and the size of `p_duo_workflows_checkpoints` when it exists.
- [ ] The 10.5.4 render is reviewed against the accepted 10.2.10 manifest and
  contains no topology, storage, ingress, or Secret-management change.
- [ ] Fresh verified Rails/Registry dumps, backup location, actual SHA-256
  values, and the Stop 6 rollback point are recorded.
- [ ] Flux source, Traefik, infrastructure Kustomizations, GitLab services,
  Gitaly, CNPG, and Valkey are all Ready with no terminating resource.

## Required manifest change

Update chart `10.2.10` to `10.5.4` only. Preserve the accepted chart-10
external-service and Registry `s3_v2` configuration.

## Window procedure

Follow the operating standard. After standard migrations and writer restore,
monitor the Duo migration separately from the synchronous acceptance path:

```bash
kubectl -n gitlab exec deploy/gitlab-toolbox -- \
  gitlab-rake gitlab:background_migrations:status
kubectl -n gitlab exec gitlab-postgres-1 -- \
  psql -U postgres -d gitlabhq_production -tAc \
  "SELECT pg_size_pretty(pg_total_relation_size('p_duo_workflows_checkpoints'));"
```

If checkpoint growth threatens the recorded free-space threshold, pause the
background migration response according to GitLab-supported operational
guidance; do not continue to cleanup merely because the Helm upgrade succeeded.

## Acceptance criteria

| Check | Expected evidence |
| --- | --- |
| Version | GitLab `19.5.3-ee`, chart `10.5.4`, deployed Helm revision, and Flux Ready. |
| Core health | Web health, CNPG, Valkey, Registry, Sidekiq, Shell, KAS, runners, and Gitaly are Ready. |
| Data and user paths | Generated DB credentials, Gitaly check, clone/push, Registry push/pull/delete, and a runner job pass. |
| Duo migration | Status and database capacity are recorded at acceptance and monitored until complete. |
| GitOps | Source and every relevant dependency Kustomization/HelmRelease are Ready at the final commit. |

## Seven-day hold and cleanup

Do not delete any old data PVC, Secret, backup, or rollback artifact during the
upgrade window. After seven stable days and completed background migrations,
open a separate, reviewed cleanup change. That change must inventory each
resource, prove it is unused, verify recoverability, and obtain explicit
approval before deletion.

## Rollback boundary and record

Rollback to the recorded Stop 6 configuration while writers are stopped when
the final application release fails acceptance. Restore a database only from
the verified Stop 7 dump and only when the incident requires it. Record dump
hashes, Helm/Flux revisions, all functional tests, Duo capacity observations,
and the seven-day cleanup decision separately.
