# Stop 2 retrospective: 18.2.8 recovery and Flux handoff

**Completed:** 2026-11-05
**Scope:** GitLab 18.2.8 / chart 9.2.8, dedicated GitLab CNPG and Valkey,
logical restore, Gitaly recovery, and return to Flux ownership.

## Outcome

- GitLab is running chart `9.2.8` under Flux management.
- GitLab uses the dedicated three-instance `gitlab-postgres` CNPG cluster and
  the authenticated, AOF-backed `gitlab-valkey` StatefulSet.
- Application database credentials are generated by the database bootstrap
  Jobs; they are not hand-maintained SOPS values.
- The Rails and Registry logical restores were verified before GitLab started.
- Gitaly is serving the retained repository PVC and passed `gitlab:gitaly:check`.
- Flux source, infrastructure dependencies, GitLab bootstrap, database
  bootstrap, GitLab, and runners all converged after the recovery.

## What happened and what we learned

| Finding | Evidence from Stop 2 | Standard for every later stop |
| --- | --- | --- |
| A logical dump is only a candidate recovery input until verified. | Four older Rails dumps were zero bytes and the usable dump's actual SHA-256 differed from its sidecar file. | Verify non-zero size and calculate SHA-256 locally; record the actual digest, source, PostgreSQL version, and dump TOC before the window. Never rely on a filename or sidecar alone. |
| Database restore success is more than a successful `pg_restore` exit. | Rails and Registry table counts, extensions, relation ownership, and application-role connections were all required to prove the restore. | Restore with `--exit-on-error`, then check table count/TOC, extensions, ownership, and connections using the generated application Secrets. |
| Generated credentials must remain generated. | The GitLab and Registry database passwords were created by bootstrap Jobs after CNPG was ready. | Keep only the CNPG superuser and Valkey auth inputs in SOPS. Do not add static application DB passwords or edit generated Secrets by hand. |
| LINSTOR control-plane health does not prove a PVC can attach. | The Gitaly replicas showed `UpToDate`, but LINSTOR reported `DeviceName None` and CSI could not attach the volume. | Require both replica health and an attachability probe: `linstor volume list` must show `/dev/drbd…`; a representative PVC must attach/mount. |
| Network namespace changes can strand legacy DRBD devices. | New satellites used pod networking while old DRBD connections used the host network namespace; `drbdadm` reported a connection in another namespace. | Confirm the live `LinstorSatelliteConfiguration` matches the versioned `worker-network` host-network policy before a window. Validate every satellite is Online after recreation. |
| A healthy Pod is not a healthy Helm/Flux release. | GitLab was available while Helm history and Flux dependency state were failed. | Acceptance requires all three: workload health, HelmRelease Ready, and the relevant Flux Kustomizations Ready at the pushed revision. |
| Flux dependencies are migration prerequisites. | A stale Traefik HelmRelease blocked `infra-controllers`, `infra-configs`, and every GitLab Kustomization. | Before suspending GitLab, require the source, `infra-controllers`, and `infra-configs` to be Ready. Record exceptions and repair them before the application window. |
| Do not delete a HelmRelease to recover a stalled release. | The real Traefik cause was a Service terminating since 2026-11-02 behind `service.kubernetes.io/load-balancer-cleanup`; deleting a HelmRelease would not have fixed it. | Inspect Helm history, the live objects, deletion timestamps, finalizers, and controller events. Repair the concrete blocking resource, then use `flux reconcile helmrelease --reset`. |
| A terminating LoadBalancer Service needs deliberate recovery. | Traefik's Service had live endpoints and the requested MetalLB IP but could not be replaced until its stale finalizer was removed. | Before clearing a finalizer, verify the requested IP, MetalLB pool/status, endpoints, and replacement manifest. Then verify the replacement has the same external IP and endpoints. |
| Direct Helm use is a recovery tool, not a substitute for Flux ownership. | A direct Traefik Helm attempt created a failed history entry because Flux owned fields. | Use direct Helm only for the GitLab suspended-window release or a documented break-glass recovery. Do not use it against unrelated Flux-owned releases without an ownership plan. |

## Corrected operational facts

- PostgreSQL endpoint: `gitlab-postgres-rw.gitlab.svc` in namespace `gitlab`.
- Valkey endpoint: `gitlab-valkey.gitlab.svc` in namespace `gitlab`.
- GitLab repository data remains on `repo-data-gitlab-gitaly-0`; never delete
  the PVC as part of an upgrade or storage recovery.
- Traefik is chart `37.1.1`. Its GitOps release now has a 15-minute Helm
  timeout and retry remediation because its CRD-heavy chart exceeded the
  former five-minute budget.
- Manual success is not the terminal state. The terminal state is a pushed
  commit plus successful Flux source and dependency reconciliation.

## Evidence required in every later change record

1. Git commit and Flux source revision before and after the stop.
2. Helm chart/release revision before and after the stop.
3. Dump file sizes, actual SHA-256 values, and off-cluster location.
4. CNPG, Valkey, LINSTOR attach, Gitaly, web health, Registry, and CI evidence.
5. A list of every deviation from the runbook, its owner, and its resolution.
