## Source-matched baseline restore rehearsals — live evidence (2026-11-13)

The obsolete bootstrap Job/ConfigMap precondition was replaced in `utility-scripts/cluster/linstor-v2-workload-restore.py` with an exact T3.6 baseline-manifest check and a uniquely matched restorable full RustFS backup. The helper verifies source handle and snapshot ID, performs an independent S3 download to a dedicated scratch LINSTOR resource, uses a deny-all network policy and read-only PVC mount, then confirms the production replica inventory and remote backup key set are unchanged before removing only isolated scratch resources. For SQLite workloads it streams only `config.xml` and database files to a private temporary directory; database bytes are not committed.

Six sources passed directly: Sonarr-1, Sonarr-2, Sonarr-4, Sonarr-6, Prowlarr, and the prior Arr Dashboard isolated T3.4 checksum restore. Sonarr-3's `sonarr.db` passed; its secondary `logs.db` had five findings in index `IX_Logs_Time`. Rebuilding that index on the private local copy yielded `integrity_check=ok`. Sonarr-5's `sonarr.db` passed, while its `logs.db` was malformed. Servarr documents that `logs.db` contains noncritical history and can be removed/recreated; the repeat drill removed only `logs.db` and its WAL/SHM sidecars from the private local copy, then confirmed the primary `sonarr.db` passed. Neither repair altered the restored PVC, source PVC, or backup. The [Sonarr recovery guidance](https://wiki.servarr.com/sonarr/faq#help-my-database-is-corrupt) documents the `logs.db` recovery path. Application boot validation remains in T7.

Radarr-4's primary `radarr.db` in the exact RustFS restore and the latest built-in Radarr archive both had B-tree/index corruption. Servarr recommends SQLite `.recover`; on a private copy from the exact restore, it produced a database with `integrity_check=ok`, zero foreign-key violations, and all 41 user tables. All scratch resources were reclaimed and production replica and RustFS key-set checks passed.
