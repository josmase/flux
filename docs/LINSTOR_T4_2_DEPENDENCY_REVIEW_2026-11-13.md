## Git bootstrap-reference remediation — 2026-11-13

The 24 in-scope PVC manifests with a Ready new-generation S3 baseline now point to that baseline snapshot and carry `kustomize.toolkit.fluxcd.io/ssa: IfNotPresent`. This leaves the immutable `dataSource` on existing bound claims alone while making the Git declaration use the current baseline if a claim is recreated. The legacy migration `VolumeSnapshot` manifests for those claims were removed from their Kustomize resource lists so a later cleanup cannot cause Flux to recreate them. The changes were rendered through Kustomize for all 24 PVCs and the rendered names, annotations, and baseline references matched the T3.6 manifest. The pinned production domain membership inventory was updated for the four boundaries whose resource sets changed.

After the first push, live Flux status exposed a separate pre-existing Radarr-1 drift: Git requested 2Gi while its Bound PVC and capacity are 4Gi, which blocked the whole media Arr reconciliation. Its T3.6 baseline is Ready. Its bootstrap declaration now points to that baseline, uses the live 4Gi request, and uses `IfNotPresent`; the old Radarr-1 migration snapshot declaration was removed from Kustomize. This does not resize or replace the existing claim.

Live Flux then showed that the shared prune-protection component replaced the PVC annotations map and stripped the `IfNotPresent` policy. The component now merges the prune annotation, preserving existing per-resource annotations. Rendered PVCs in the affected production domains contain both `prune: disabled` and `ssa: IfNotPresent`; the follow-up commit is required before Flux can safely apply the manifests.

This updates the future restore path without changing existing claims. Flux applied revision `81aa4a66` successfully to the affected production domains. All 25 relevant PVCs (the 24 old-source claims plus Radarr-1) remain Bound with their original UIDs; the 24 old migration `VolumeSnapshot` objects are still present, all 25 new baseline snapshots remain Ready, and no snapshot or backend artifact was deleted. T4.2 remains blocked on the unresolved Radarr-6 v1 and Reiverr cases, five orphan contents, CNPG and historical dependency mapping, the LINSTOR remote catalog timeout, and user-deferred Artifactory/Immich records.

## LINSTOR/RustFS timeout fix — 2026-11-13

The affected controller is LINSTOR `v1.34.2`. Error report `6AF583DC-00000-000143` showed LINSTOR’s AWS SDK `ListObjectsV2` request timing out at the configured five-second default. LINSTOR source confirms the controller property is `BackupShipping/BackupTimeout` (seconds); the initially attempted key `BackupShipping/Timeout` was rejected without changing configuration. Set the supported controller property to `60`. The catalog then returned 103 LINSTOR records and one `other` metadata object, and an exact-ID dry-run completed for an in-scope old record, listing its data and `.meta` object keys. The property reads back as 60, and a Flux-managed one-shot Job now ensures the value is present without reapplying it when already correct. Health after the property update: 234 UpToDate and 6 Diskless resource volumes; LinstorCluster Applied/Available/Configured are all True. No artifact was deleted. T4.2 remains blocked on the dependency/recovery gates above.
